# codix — Phase 2 Step-by-Step Plan

Step-by-step plan for phase 2 (daemon and MCP) of
`docs/2026-11-04-original_implementation_plan.md`, as that plan requires when a
phase starts. Task numbers and scope are the implementation plan's; this document
adds the order of work, the choices each task left open, the crate versions, and
the steps inside each task. Each task lands as one reviewed change, on its own
branch, with its tests, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check` and the full test suite green on the three CI platforms.

## Choices made before phase 2

These were checked on 2026-11-05 with a throwaway probe (Rust 1.99.1,
aarch64-apple-darwin), not taken from memory.

| Question | Choice | Evidence |
| --- | --- | --- |
| Local socket (2.1) | `interprocess` local sockets: Unix domain socket on Unix, named pipe on Windows, blocking API | One API for both transports and both name kinds (file path, pipe namespace); `std::os::unix::net` has no Windows counterpart, and named pipes through `windows-sys` would need `unsafe` |
| Daemon concurrency (2.1) | Threads: one per connection, one writer, one watcher; no async runtime in the daemon | Requests are short and CPU-bound on SQLite and tree-sitter; the existing scan already runs on `rayon` |
| File watcher (2.3) | `notify` 8.2.1 (stable), `RecommendedWatcher`; debouncing written here | 9.0 is still a release candidate, as is `notify-debouncer-full` 0.8; the debounce is a ~30-line loop over `recv_timeout` |
| MCP server (2.5) | `rmcp` 3.9.0, the official SDK, features `server` and `transport-io`, with `ServerHandler` implemented by hand (tools built at runtime, no `#[tool]` macros) | Compiles under `unsafe_code = "forbid"`; protocol version `2026-07-28`. It brings `tokio`, which stays inside `codix-mcp` (83 crates in the probe's tree). The alternative, JSON-RPC written here (~300 lines, std only), would leave codix tracking spec changes (version negotiation, cancellation, structured output) by hand |
| JSON Schema (2.5, 2.6) | `schemars` 1.2.3 derives on every request and response type | Draft 2020-12 output, doc comments become `description`, `Option` becomes nullable; the same schema serves MCP `inputSchema`, `outputSchema` and the 2.6 snapshots |
| Process memory (2.1, 2.8) | `sysinfo`, already a dependency, with its `system` feature added | Safe API on the three platforms; used for `daemon list` and the 2.8 memory figure |
| Detaching the daemon (2.1) | `std::process::Command`: `process_group(0)` on Unix, `creation_flags(DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP)` on Windows, stdio to null and `.codix/daemon.log` | Std only, no `unsafe`, no daemonizing crate |
| Wire framing (2.2) | Newline-delimited JSON, one request and one response at a time per connection | Compact JSON never contains a raw newline; readable in logs and testable with `std::io::pipe` |
| Text rendering for MCP (2.5) | `codix-cli/src/render.rs` moves to `codix-core::render`, returning strings; color stays a flag the CLI sets | MCP results carry the same text as the CLI; a separate `codix-render` crate would add a crate for one module |

### Sandbox findings

The probe also showed that the Claude Code sandbox on this Mac refuses binding a
Unix socket (`EPERM`, in `$TMPDIR` and in the project) and starting an FSEvents
stream (`unable to start FSEvent stream`). The design is unchanged. Decided
for testing:

- Protocol, debounce and batch logic are tested without sockets or watchers,
  and run everywhere.
- Tests that need a real socket or watcher have names starting with `live_`.
  CI runs them on its three platforms and is their check. Locally, inside the
  sandbox, the suite runs with `--skip live_`; CI never skips them.

## New crates

Per the implementation plan's layout:

- `codix-daemon`: daemon process, runtime registry, socket protocol (server and
  client), watcher. Depends on `codix-core`, `interprocess`, `notify`, `sysinfo`.
- `codix-mcp`: the MCP router. Depends on `codix-core`, `codix-daemon`, `rmcp`,
  `tokio`.

`codix-cli` depends on both. Neither is a Cargo feature: the design lists
`daemon` and `mcp` as commands of every build, `minimal` included.

## Order of work

Tasks run in the implementation plan's order. Three dependencies need a decision
on where code first appears:

- **2.1 needs a protocol.** Starting, stopping and listing daemons needs a
  handshake. 2.1 introduces the transport and the control messages (`hello`,
  `stop`, `stats`); 2.2 adds operation requests on the same framing.
- **2.5 needs schemas.** MCP input and output schemas come from `schemars`
  derives, added in 2.5. 2.6 adds the snapshots and the versioning check.
- **2.4 before 2.5.** MCP tool descriptions are the canonical descriptions.

## Tasks

### 2.1 Daemon lifecycle

1. **Write gate in core.** Today `scan_within` and `rescan` take
   `.codix/write.lock` themselves. A daemon holds that lock for its lifetime, and
   a second `File::lock` in the same process would block on itself, so writes go
   through a `WriteGate` held by `Context`:
   - `FileGate`: the current behavior, the OS lock per write, polled up to the
     wait;
   - `HeldGate`: the daemon's, an in-process mutex over the lock it already holds,
     polled the same way.
   `Context::discover` builds a `FileGate`; the daemon builds contexts with its
   `HeldGate`. Call sites in `query`, `indexing` and `config` take the gate from
   the context. No behavior change without a daemon; the existing tests cover it.
2. **Socket name.** `.codix/daemon.sock` when its path fits `sun_path` (104 bytes
   on macOS, 108 on Linux); otherwise `<runtime dir>/<root hash>.sock`. Windows:
   `\\.\pipe\codix-<root hash>`. Root hash: the first 16 hex digits of BLAKE3 over
   the canonical root.
3. **Runtime directory.** Linux: `$XDG_RUNTIME_DIR/codix`, else
   `<temp dir>/codix-<user>` created with mode 0700. macOS: `$TMPDIR/codix`
   (per user). Windows: `%LOCALAPPDATA%\codix\run`. `CODIX_RUNTIME_DIR`
   overrides it, for tests (documented as such, like
   `CODIX_TEST_ASSUME_NETWORK_FS`).
4. **Control protocol.** Frames as in 2.2. `hello` (protocol number and codix
   version → root, version, PID, socket), `stop`, `stats` (memory, idle time,
   start time). These three messages keep their shape across codix versions, so
   any client can identify and stop any daemon.
5. **Startup**, in `codix daemon run --root <root>` (hidden, foreground):
   1. take `.codix/daemon.lock` with `try_lock`; busy → `daemon_running`
      (new error code, exit 4) naming the PID and socket from `daemon.json`;
   2. take `.codix/write.lock`, waiting as long as an in-process `index` holds it;
   3. remove a leftover socket file, bind, write `.codix/daemon.json` (root,
      socket, PID, version, protocol) and the registry entry
      `<runtime dir>/daemons/<root hash>.json`;
   4. serve; the startup scan of 2.3 runs on the writer thread meanwhile.
   The OS releases both locks when the process dies, so a crash never blocks the
   next start; `daemon.json` left behind is detected as stale by a failed
   connection.
6. **Commands.**
   - `daemon start [--root]`: spawns `daemon run` detached and waits up to 10 s for
     `hello`; prints root, PID and socket. A running compatible daemon →
     `daemon_running`. A running incompatible one (other version or protocol) is
     stopped and replaced.
   - `daemon stop [--root] [--all]`: `stop` over the socket, then waits for
     `daemon.lock` to be released (10 s). `--all` stops every registered daemon.
   - `daemon list`: every registry entry, checked with `hello` (dead ones
     removed), with project, PID, memory and idle time from `stats`.
   - `status` gains a `daemon` line: PID, uptime, idle time, or "not running".
7. **Idle stop.** New local key `daemon.idle_timeout` (duration, default `30m`,
   effect "applies at the next daemon start"). Only requests reset the idle
   clock; watcher activity does not.
8. **Clean exit** removes the socket, `daemon.json` and the registry entry, in
   that order, then releases the locks.

**Tests:** gate unit tests (held gate times out, file gate unchanged); two
projects side by side, each with its own daemon; a nested project and a git
worktree of the same repository each get their own daemon; second `start` fails
naming the first; `daemon.json` from a killed daemon replaced on start; a daemon
reporting another version replaced (version injected through a test-only
variable); a root path long enough to force the runtime-directory socket;
`list` and `stop --all` over two daemons; idle stop with a 1 s timeout.

### 2.2 Socket protocol

1. **Errors on the wire.** `Error` is not serializable today. An `ErrorReport`
   (code, cause, hint, candidates, exit code) is built from `Error`; the CLI
   renders errors from `ErrorReport` on both paths, so they cannot differ.
2. **Frames.** Request
   `{"op": <Operation::NAME>, "cwd": <absolute>, "root": <--root or null>,
   "request": <Operation::Request>}`; response
   `{"result": <Operation::Response>, "warnings": [...]}` or
   `{"error": <ErrorReport>, "warnings": [...]}`.
3. **Dispatch.** A table in core from operation name to a function that
   deserializes the request, runs the operation against a context built from
   the client's cwd and the daemon's gate, and serializes the response. A test
   checks that every `Operation` is in it.
4. **Daemon side.** The project and its config are opened once and reused;
   each request only builds the cwd-dependent part of the context. A request
   whose cwd resolves to another root gets `usage` naming both roots.
5. **CLI side.** Before running an operation: read `daemon.json`; no file, or
   connection refused → in-process. `hello` mismatch → stop that daemon, warn
   `daemon_stopped` (with the hint `codix daemon start`), run in-process, since a
   stale daemon would hold the write lock. Otherwise send the request and render
   the typed response with the same code as in-process.
6. **Which commands go through the daemon:** every operation (`index`, `status`,
   `config`, `capabilities`, the queries; `init` on an already initialized
   project). `daemon` and `mcp` never do.

**Tests:** the server loop over `std::io::pipe` pairs, without a socket
(framing, unknown operation, malformed frame, error round trip); then every
golden case of phase 1 run in-process and through a daemon on the same fixture,
with stdout, stderr and exit code compared byte for byte.

### 2.3 Watch mode

1. **Writer thread.** One thread in the daemon owns the scan pipeline: the
   startup full scan, the periodic full scan, watcher batches, and requests'
   rescans, all serialized through the `HeldGate`.
2. **Watcher.** `notify::RecommendedWatcher` (FSEvents, inotify,
   ReadDirectoryChangesW). On macOS and Windows one recursive watch on the root.
   On inotify, which needs one watch per directory and is where the quota
   bites, codix adds a non-recursive watch per indexed directory (from the
   `dirs` table) and one on each directory created later, so it knows exactly
   which directories are unwatched.
3. **Debounce.** Events are collected until 100 ms pass without a new one, or
   1 s in total; then the batch is processed.
4. **Partial scan.** New core function `scan_dirs(dirs)`: the walker run on only
   those directories, with the same ignore rules (parent ignore files included),
   compared with the manifest rows under them. A batch maps each event to its
   parent directory, and a created or removed directory to its whole subtree.
   Ignored paths therefore never reach the parser.
5. **Periodic scan.** Full stat scan at startup and every `index.scan_interval`
   (existing local key, `10m`; effect changes to "applies at the next daemon
   start").
6. **Quota fallback.** A failed watch adds the directory to an unwatched set.
   While it is not empty the periodic scan runs every minute instead, and
   `status` says "watching N directories; M unwatched, rescanned every minute".
   `CODIX_TEST_MAX_WATCHES=<n>` caps the watches added (per-directory mode on
   every platform), for tests only.
7. **Queries.** Lookups keep their phase 1 recheck of the returned files, so a
   result is never older than the file on disk, whatever the debounce. `grep`
   skips its full pre-scan when nothing is unwatched and only flushes the pending
   batch; with unwatched directories it scans as in phase 1.
8. **Self-writes.** The implementation plan adds a self-write registry. A
   registry is not needed: an apply (phase 3) updates the manifest with the new
   stats, so the watcher's event finds the file's stats equal to the manifest's
   and does not read it. 2.3 tests this with a write followed by a forwarded
   `rescan`; phase 3 reuses the test for `apply`.
9. **`codix watch`.** The design lists `watch` among the index commands; no task
   places it. It is `daemon run` with output on stderr: the daemon in the
   foreground, until interrupted.

**Tests:** the debounce and batch mapping as unit tests over synthetic events;
an edit, a create, a delete and a directory rename each visible to the next
query without a manual `index`; an event for an ignored file causes no parse;
dropped events (watcher replaced by one that drops everything) recovered by the
periodic scan with a 1 s interval; quota fallback with
`CODIX_TEST_MAX_WATCHES=1`, reported in `status`; a self-write causes no
reparse; reindex after one save < 50 ms, measured from the end of the debounce
to the commit (see Open points).

### 2.4 Canonical descriptions and discovery

1. **Table.** `codix-core::describe::COMMANDS`, one `Description` per command
   (operations and the `daemon`, `watch`, `mcp` commands): name, summary (one
   line), when to prefer it over grep, what it returns, minimum tier, one
   example. Short: each one costs context in every MCP session.
2. **CLI.** clap's `about` is the summary and `long_about` the full description,
   set from the table at startup (`Command::mut_subcommand`), replacing the
   doc comments. `codix help <command>` is clap's built-in `help`, which prints
   the long help: description, flags, example.
3. **Flags.** Each request field's doc comment (seen by `schemars` in 2.5) and
   the matching clap argument's help are the same text.
4. **`capabilities`** gains the dynamic part when run in a project: operations
   with their minimum tier; languages present in the index with file counts and
   tier; index status (files, pending, last scan); the daemon, if any. Outside a
   project it prints the static part, as today.
5. **`languages`**: every known language with its tier, extensions and
   filenames, and whether it is compiled into this build.
6. **`init --agent-docs [<path>]`**: writes a short workflow guide (find →
   outline → show → grep in phase 2; preview → apply arrives in phase 3)
   generated from the table, to `CODIX.md` at the root or `<path>`. It
   overwrites only a file that starts with codix's generated-file marker, and
   otherwise fails with `file_exists` (new code, exit 4).
7. **Generated docs.** `docs/commands.md`, generated from the table and kept
   current by a golden test.

**Tests:** a command without a description or example fails a test; every
operation has a description; CLI flag help equals the request field's
description; golden `help find`, `languages`, `capabilities` in a project,
`docs/commands.md`; `--agent-docs` refusing a hand-written file.

### 2.5 `codix mcp`

1. **Schemas.** `schemars::JsonSchema` derived on every request and response
   type in core.
2. **Rendering.** `render.rs` moves to `codix-core::render` (see Choices); the
   CLI keeps terminal detection, color and stderr.
3. **Server.** `rmcp` over stdio, `ServerHandler` written by hand:
   - `tools/list`: one tool per operation, same name as the CLI command,
     description from 2.4, `inputSchema` from the request type plus an optional
     `cwd`, `outputSchema` from the JSON envelope around the response type;
   - `tools/call`: `content` is the text rendering, exactly as the CLI prints it
     without color; `structuredContent` is the JSON envelope the CLI's `--json`
     prints; an error sets `isError` with `error[code]: …` as text and the error
     envelope as structured content.
4. **Router.** `cwd` (absolute, or relative to the server's start directory,
   which is the default) → project discovery → that root's daemon, through the
   2.2 client, started as `daemon start` does when none is running. Daemon calls
   run on `tokio::task::spawn_blocking`. Paths in results are relative to `cwd`,
   because the request carries it. Several MCP servers on one project share its
   daemon.
5. **`init` through MCP.** A project with no `.codix/` has no daemon: `init`
   runs in-process, then starts the daemon; any other tool there returns
   `not_indexed` with a hint naming the `init` tool.
6. **Not tools:** `daemon`, `watch`, `mcp`, `help` (the descriptions are already
   in `tools/list`).

**Tests:** JSON-RPC over the server's stdin and stdout from the test (no MCP
client crate): `initialize`, `tools/list` names equal the CLI's operation
commands, input properties equal the CLI flags per tool, calls against two
projects from one server, two calls in flight at once, an error result, results'
text identical to the CLI's for the same command.

### 2.6 Output schema versioning

1. `SCHEMA_VERSION` moves from the CLI to core; the CLI and MCP envelopes both
   use it.
2. Snapshots: `schemas/v<N>/<command>.request.json`, `<command>.response.json`,
   `envelope.json`, `error.json`, generated from the `schemars` derives;
   `CODIX_BLESS=1` rewrites them.
3. A test fails on any difference between the generated schemas and the
   snapshots. Its message classifies the difference:
   - additive (new optional property, new command): bless;
   - breaking (property removed or renamed, type changed, request property newly
     required, enum value removed): increment `SCHEMA_VERSION`, which moves the
     snapshots to `schemas/v<N+1>/`.
   Blessing a breaking difference without the increment fails the same test.

**Tests:** the classifier on hand-made schema pairs, one per rule; the snapshot
test itself.

### 2.7 LLM benchmark, first run

1. `eval/tasks/<id>.toml`: about 20 tasks on the pinned spring-framework
   checkout of the benchmarks (locate a type or method, follow a definition
   through `show`, read a package's outline), each with its prompt, category,
   and expected answer (set of `path:line` or symbol IDs).
2. Harness: a Rust crate, `codix-eval`, in the workspace (std and `serde_json`
   only; it reuses the benchmarks' pinned-repository download). For each task
   and model it runs Claude Code headless:
   `claude -p <prompt> --model <model> --mcp-config <codix mcp only>
   --strict-mcp-config --tools "" --allowedTools "mcp__codix__*"
   --setting-sources "" --no-session-persistence
   --output-format stream-json --verbose`, in the checkout. The model sees only
   codix's MCP tools, as `tools/list` returns them, and no instructions about
   codix. The stream gives every tool call, its result, turns and tokens.
3. Models: `haiku`, `sonnet` and `opus`, through your Claude Code login: no API
   key. The harness cannot run inside this Claude Code sandbox (no access to
   the login); you run it with `! cargo run -p codix-eval --release`.
4. Per run: success, turns, tool calls, tokens, and defects, each with its
   transcript excerpt:
   - misused command (an error of class `usage` or `ambiguous_symbol` left
     unresolved),
   - guessed flag (an input property not in the schema),
   - grep fallback (`grep` called for a locate task that `find` or `def`
     answers).
5. Results in `eval/results/<version>.json` and a summary table in
   `eval/README.md`. Defects lead to proposed changes to names or descriptions,
   listed in the phase report; they are not part of this task.

**Done when** every model has run every task once and the results are recorded.

### 2.8 Phase exit

1. `benches/` gains, with the release binary on spring-framework (1.6M lines):
   - daemon query p95: `find`, `def`, `outline`, `show` through the CLI with a
     running daemon, process start included;
   - the same through MCP, from request to result;
   - daemon memory (RSS from `stats`) after the cold index and 1,000 queries;
   - reindex after one save, as defined in 2.3.
2. Results in `benches/results/0.2.0.json`; workspace version 0.2.0.
3. README: daemon, `watch`, MCP setup (`claude mcp add codix -- codix mcp`),
   `help`, `languages`, `--agent-docs`.

**Done when** the targets (query p95 < 10 ms, memory < 500 MB, reindex < 50 ms)
are met or each miss is reported with its figure.

## Deviations from the implementation plan

- **No self-write registry** (2.3, step 8): the manifest already plays that
  role.
- **`codix watch` placed in 2.3**: the design lists it; the implementation
  plan's known gap 2 missed it.
- **New error codes**: `daemon_running`, `file_exists` (exit 4), and the warning
  `daemon_stopped`.

## Open points

- **2.8 benchmarks.** They need a running daemon, so they cannot run in this
  Claude Code sandbox, and CI timings are too noisy for the targets: they need
  a local run outside the sandbox.
- **Reindex target versus debounce.** The 100 ms debounce is longer than the
  50 ms reindex target. This plan measures the target from the end of the
  debounce; queries never see a stale file anyway, because they recheck the
  files they return.
- **Known gaps 1 and 5** stay with phases 3 and 4.
